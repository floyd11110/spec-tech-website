PHASE 3 / PERIPHERAL CONVENIENCE LAYER

STPulse v0.1.0-DEV

Detailed reference for the current basic pulse-measurement layer using Arduino pulseIn().

Purpose

Measurements

High pulse width, low pulse width, period, frequency, duty cycle, and RPM conversion.

Current architecture

This first version is deliberately blocking and uses pulseIn(). It is intended for basic measurement and diagnostics, not deterministic high-speed capture.

Validated wiring

Arduino Nano D9 generated a 100 Hz test signal with tone(); D7 was the STPulse input.

Validated wiring

Nano D9  -------->  Nano D7

D9 = tone() source
D7 = STPulseInput

Basic use

#include <STPulse.h>

STPulseInput pulse(7, 50000UL);

void setup()
{
    pulse.begin();
    tone(9, 100);
}

void loop()
{
    float hz = pulse.frequencyHz();
    float rpm = pulse.rpm(1);
}

API reference

FunctionMeaningStatus
begin()Initializes the input according to the configured mode.PASS
highWidth()Measures HIGH pulse width in microseconds.PASS
lowWidth()Measures LOW pulse width in microseconds.PASS
periodMicros()Returns measured signal period in microseconds.PASS
frequencyHz()Converts measured period to frequency in hertz.PASS
dutyCycle()Returns approximate HIGH duty cycle percentage.PASS
rpm(PPR)Converts frequency to RPM using pulses per revolution.PASS
setTimeout(us)Changes pulseIn timeout in microseconds.PASS
timeout()Returns configured timeout.PASS
pin()Returns input pin.PASS
mode()Returns configured input mode.PASS

Measurement relationships

Period_us = HIGH_us + LOW_us

Frequency_Hz = 1,000,000 / Period_us

Duty_% = HIGH_us / Period_us × 100

RPM = Frequency_Hz × 60 / PulsesPerRevolution

Hardware validation at 100 Hz

HIGH ≈ 4950 us
LOW ≈ 4963–4970 us
PERIOD ≈ 9913–9920 us
FREQ ≈ 100.81–100.89 Hz
DUTY ≈ 49.9 %
RPM(1 PPR) ≈ 6048–6053

The measured values are consistent with the D9 100 Hz tone test and the blocking pulseIn()-based measurement method.

Pulses per revolution

At ~100.89 Hz:

1 PPR  -> 6051.4 RPM
2 PPR  -> 3025.7 RPM
20 PPR -> 302.7 RPM

Increasing PPR reduces calculated mechanical RPM for the same electrical pulse frequency because more pulses represent each revolution.

Timeout and no-signal behavior

Initial timeout = 50000
After setTimeout(20000) = 20000

Signal stopped:
HIGH = 0
LOW = 0
PERIOD = 0
FREQ = 0.00

This confirms the current no-signal convention: zero-valued measurement results after the configured timeout.

Blocking limitation

Important

Each pulseIn()-based measurement can block until the requested pulse completes or the timeout expires. This version is suitable for basic measurement, but not for precision multi-channel high-speed capture or time-critical control.

Future architecture

A later separate layer should use external interrupts and/or hardware timers for non-blocking edge timestamping, frequency/count windows, and higher-precision capture. That future implementation should remain distinct from this simple blocking STPulse v0.1.0 API.
