Design philosophy

Compatibility first

ST helper APIs sit on top of ordinary Arduino behavior. They do not replace the Arduino execution model.

No hidden scheduler

Digital I/O helpers do not require a background task, hidden interrupt, heap allocation or mandatory runtime service.

Explicit update model

Debounced input state is refreshed only when the application calls button.update(). This keeps timing and execution visible to the programmer.

Low overhead

The convenience layer is intended to remain lightweight and suitable for the ATmega328P resource envelope.

Raw-read timing note.

Each raw helper may sample the physical pin independently. A mechanical button can bounce between calls, so a sequence such as read(), isHigh() and isLow() is not guaranteed to represent one identical instant. Use the debounced cached API below when one coherent stable state is required.

Debounce & edge detection

The v0.2.0 input layer adds a non-blocking debounce state machine. The application explicitly calls update(); all stable-state and edge results for that update are derived from the cached debounced state.

State API

  • update() — sample/process the input
  • stableRead() — cached debounced HIGH/LOW
  • stableHigh() — stable state is HIGH
  • stableLow() — stable state is LOW
  • changed() — stable state changed on this update

Edge & configuration API

  • rose() — debounced LOW → HIGH transition
  • fell() — debounced HIGH → LOW transition
  • setDebounce(ms) — changes debounce interval
  • debounceMs() — reports configured interval
Overflow-safe timing principle.

Debounce timing should use unsigned elapsed-time subtraction rather than absolute-time comparison so normal millis() wraparound does not break the interval test.

Validated press/release example

#include <STDigitalIO.h>

STDigitalOutput led(13);
STDigitalInput button(2, INPUT_PULLUP, 30);

void setup()
{
    Serial.begin(115200);
    led.begin(false);
    button.begin();
}

void loop()
{
    button.update();

    if (button.fell())
    {
        Serial.println("PRESSED / FELL");
        led.toggle();
    }

    if (button.rose())
    {
        Serial.println("RELEASED / ROSE");
    }
}

Known limitations & engineering rules

  • update() must be called frequently enough for the required button/input response time.
  • A long blocking operation in the user loop can delay debounce recognition because there is intentionally no hidden background scheduler.
  • Mechanical debounce is appropriate for slow human-operated contacts; do not use it to intentionally filter high-speed pulse inputs.
  • High-speed timing/counting belongs to hardware-timed acquisition or a dedicated high-speed module when deterministic capture is required.
  • The current validation target is the Arduino Nano / ATmega328P checkpoint; other MCU families require their own regression evidence.

Release decision

Current decision

Keep STDigitalIO v0.2.0-DEV as the validated lightweight digital I/O layer for the current Nano development checkpoint.

Next development direction

STDigitalIO and STAnalogIO are the current hardware-validated Phase 2 convenience layers. Continue adding similarly explicit, low-overhead APIs without introducing a scheduler or hidden runtime dependency into Arduino Compatibility mode.
