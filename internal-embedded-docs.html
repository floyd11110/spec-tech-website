ST EMBEDDED DOCUMENTATION

STDigitalIO v0.2.0-DEV

Detailed usage guide, behavior explanation, practical examples, validation notes, and common mistakes for the current Arduino Nano / ATmega328P checkpoint.

1. What STDigitalIO is

Purpose

STDigitalIO is a lightweight convenience layer over ordinary Arduino digital I/O. It gives clearer object-style functions such as led.on(), led.off(), button.isLow(), and debounced edge functions such as button.fell().

What it does not do

It does not replace Arduino setup() and loop(), does not require ST.run(), and does not install a hidden scheduler or background task.

Execution model

Raw functions read the pin when called. Debounced functions use an explicit update() call so the programmer controls when the input is sampled and processed.

2. Creating digital output and input objects

Digital output

STDigitalOutput led(13);

This creates an ST output object connected to Arduino digital pin 13.

Important: the constructor identifies the pin, but the pin is not ready as an output until led.begin(...) is called in setup().

Digital input

STDigitalInput button(2, INPUT_PULLUP);

This creates an ST input object connected to D2 and configured for Arduino INPUT_PULLUP mode.

Important: call button.begin() inside setup() before reading the input.

3. STDigitalOutput — complete explanation

begin(false)

Configures the selected pin as an output and initializes it LOW.

STDigitalOutput led(13);

void setup()
{
    led.begin(false);
}

Expected physical result: LED/output starts OFF.

begin(true)

Configures the output and initializes it HIGH immediately.

void setup()
{
    led.begin(true);
}

Expected physical result: LED/output starts ON.

on() and off()

These are convenience functions for forcing the output HIGH or LOW.

led.on();   // HIGH
delay(1000);

led.off();  // LOW
delay(1000);

write(bool)

Use this when the desired output state comes from a variable or condition.

bool desiredState = true;
led.write(desiredState);

true means HIGH. false means LOW.

When is write() better than on()/off()?

Use on() or off() when the state is fixed by the instruction. Use write(x) when the state is calculated, stored in a variable, or copied from another condition.

toggle()

Reverses the currently tracked output state.

void loop()
{
    led.toggle();
    delay(200);
}

If the LED is OFF, it becomes ON. If it is ON, it becomes OFF. Repeating this creates a blink.

state()

Returns the output state tracked by the STDigitalOutput object.

Serial.println(led.state());

Observed validation behavior: after led.off(), state() returned 0; after led.on(), it returned 1.

pin()

Returns the Arduino pin number assigned to the object.

Serial.println(led.pin());  // expected 13

This is primarily useful for diagnostics, logging, inspectors, and generic helper code.

4. STDigitalInput — raw input functions

begin()

Applies the configured Arduino input mode.

STDigitalInput button(2, INPUT_PULLUP);

void setup()
{
    button.begin();
}

read()

Reads the pin immediately and returns the raw digital level.

int state = button.read();

if (state == HIGH)
{
    led.on();
}
else
{
    led.off();
}

isHigh() and isLow()

These are readable alternatives to comparing read() with HIGH or LOW.

if (button.isHigh())
{
    led.on();
}

if (button.isLow())
{
    led.off();
}

pin() and mode()

These expose object configuration information.

Serial.println(button.pin());

if (button.mode() == INPUT_PULLUP)
{
    Serial.println("Button uses INPUT_PULLUP");
}

5. INPUT_PULLUP — why released means HIGH

With INPUT_PULLUP, the microcontroller enables an internal pull-up resistor. The input naturally sits HIGH when the switch is open. Pressing a button connected from the input pin to GND pulls the signal LOW.

Button conditionElectrical resultCode meaning
ReleasedHIGH / 1button.isHigh() is true
PressedLOW / 0button.isLow() is true
if (button.isLow())
{
    // For INPUT_PULLUP this normally means:
    // BUTTON IS PRESSED
}
Common confusion

A beginner may expect “pressed = HIGH,” but INPUT_PULLUP is normally active-low when the button connects the pin to GND.

6. Why the raw test produced contradictory readings

During one regression test, output similar to the following appeared:

button.read() = 0
button.isHigh() = FALSE
button.isLow() = FALSE

This does not necessarily mean the three functions are logically broken. Each raw function can perform a separate physical read. A mechanical button can bounce rapidly during press or release, so the pin can change between those calls.

Conceptually:

button.read();    // sample at time A
button.isHigh();  // sample at time B
button.isLow();   // sample at time C

If the switch contact changes between A, B, and C, the results no longer describe one single instant.

7. Mechanical button bounce

A mechanical switch does not always change cleanly from HIGH to LOW once. Its metal contacts can physically bounce for a short time and produce a rapid sequence of transitions.

Ideal press:
HIGH ---------------- LOW

Real mechanical press may look like:
HIGH -- LOW -- HIGH -- LOW - HIGH - LOW ---- LOW

Without debounce, one physical press may be interpreted as several presses.

8. Debounced input model

STDigitalInput v0.2.0 adds an explicit non-blocking debounce mechanism. The key function is:

button.update();
  1. The application calls update().
  2. The library samples the raw input.
  3. If the raw state changed, a debounce timing window begins or restarts.
  4. The new raw state must remain stable for the configured debounce interval.
  5. Only then does the library accept the new stable state.
  6. On that accepted change, changed(), rose(), or fell() can report the event.

This approach does not use a blocking delay() for debounce.

9. update() — why it must be called

The debounce system is deliberately explicit. There is no hidden task that keeps reading the input in the background.

void loop()
{
    button.update();

    // Use debounced functions after update()
}
If you forget update()

The debounced state cannot process new raw samples, so stableRead(), changed(), rose(), and fell() will not reflect new button activity correctly.

10. Stable-state functions

stableRead()

Returns the accepted debounced state rather than an immediate raw sample.

stableHigh()

Returns true when the accepted stable state is HIGH.

stableLow()

Returns true when the accepted stable state is LOW.

button.update();

if (button.stableLow())
{
    // stable pressed state for INPUT_PULLUP
}

11. Edge detection: rose() and fell()

An edge means a transition from one stable digital state to the other.

FunctionTransitionINPUT_PULLUP button meaning
rose()LOW → HIGHButton released
fell()HIGH → LOWButton pressed

One toggle per press

#include <STDigitalIO.h>

STDigitalOutput led(13);
STDigitalInput button(2, INPUT_PULLUP, 30);

void setup()
{
    led.begin(false);
    button.begin();
}

void loop()
{
    button.update();

    if (button.fell())
    {
        led.toggle();
    }
}

This differs from testing button.isLow() continuously. With fell(), the action occurs only on the accepted HIGH-to-LOW transition, not during the whole time the button is being held.

12. changed()

changed() becomes true when the stable debounced state changes during the current update cycle.

button.update();

if (button.changed())
{
    Serial.print("New stable state: ");
    Serial.println(button.stableRead());
}

Use this when you care that a transition happened but do not need to distinguish rising from falling immediately.

13. Setting debounce time

Constructor setting

STDigitalInput button(2, INPUT_PULLUP, 30);

The third argument configures a 30 ms debounce interval.

Runtime setting

button.setDebounce(50);

This changes the debounce interval to 50 ms.

Reading the configured value

Serial.println(button.debounceMs());

Hardware regression confirmed 30 ms from construction and 50 ms after setDebounce(50).

15. Practical examples

Example A — LED follows raw button state

#include <STDigitalIO.h>

STDigitalOutput led(13);
STDigitalInput button(2, INPUT_PULLUP);

void setup()
{
    led.begin(false);
    button.begin();
}

void loop()
{
    if (button.isLow())
    {
        led.on();
    }
    else
    {
        led.off();
    }
}

For INPUT_PULLUP: pressed = LED ON, released = LED OFF.

Example B — copy a boolean state to an output

bool alarmActive = true;
led.write(alarmActive);

Example C — toggle only once per press

button.update();

if (button.fell())
{
    led.toggle();
}

Example D — print every stable input change

button.update();

if (button.changed())
{
    Serial.print("Stable input = ");
    Serial.println(button.stableRead());
}

Example E — separate press and release actions

button.update();

if (button.fell())
{
    Serial.println("Button pressed");
    led.on();
}

if (button.rose())
{
    Serial.println("Button released");
    led.off();
}

18. Engineering limitations

  • Current validation is for the Arduino Nano / ATmega328P checkpoint.
  • The library remains DEV even though the current implemented API has hardware-validated behaviors.
  • Debounce response depends on how often update() is called.
  • Long blocking code can delay event recognition because no hidden scheduler exists.
  • Mechanical debounce must not be treated as a high-speed pulse acquisition method.
  • Other MCU families require separate regression and timing verification.
